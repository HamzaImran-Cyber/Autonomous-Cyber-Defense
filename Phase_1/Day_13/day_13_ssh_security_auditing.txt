4. ARCHITECTURAL REAL-WORLD APPLICATION & PROBLEM SOLVING
------------------------------------------------------------------------------
[Audit Target 1: Written Config vs. Runtime Defaults (`sshd -T`)]
* Purpose: Compares lines written inside `/etc/ssh/sshd_config` against what the server actually enforces in memory.
* Security Risk: Many settings in configuration files are commented out with `#`, relying on built-in defaults that might not be obvious at first glance.
* Practical Action: Querying `sshd -T` confirms that the server defaults to safe options like `permitrootlogin prohibit-password`.

[Audit Target 2: Root Login Rules (`permitrootlogin prohibit-password`)]
* Purpose: Controls whether the main administrator (`root`) can log in remotely over the network.
* Security Risk: Allowing password logins directly as `root` invites automated guessing attacks against the most powerful account on the machine.
* Practical Action: Confirmed that root cannot log in using a password. Remote root logins are strictly restricted to verified SSH key pairs.

[Audit Target 3: Secret Host Key Permissions (`-rw-------`)]
* Purpose: Inspects file permissions on the server's private identity keys (`ecdsa`, `ed25519`, `rsa`).
* Security Risk: If standard users can read these private keys, they can impersonate the server and steal encrypted traffic.
* Practical Action: Confirmed that all private key files enforce strict `-rw-------` permissions, meaning only `root` can access them.

5. KEY TECHNICAL LESSONS
------------------------------------------------------------------------------
* Commented lines (`#`) in `/etc/ssh/sshd_config` mean the server falls back to its built-in system defaults.
* Always use `sshd -T` to verify what rules the SSH server is actively enforcing in memory.
* Secret server host keys must strictly stay locked to `0600` (`-rw-------`) owned by `root:root`.
